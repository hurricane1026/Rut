# Rut 与 nginx 性能对比 2026 年 10 月 2 日

当前合并版本在 96 个 HTTP/1.1 坐标中有 78 个吞吐领先 nginx，60 个达到至少快 10% 的目标。576 个正式样本与全部预热均无网络或状态错误，所有坐标完成响应预检。仍有明确的性能缺口：完整响应缓冲代理的 64 KiB 单连接和 1 MiB 响应、HTTP 1 MiB 静态长连接，以及 HTTPS 1 MiB 代理的高并发。反转测量顺序并延长采样后，主要落后点仍然存在。

## 测量条件

- Rut 源码为干净的 `e54b32bc5e98803cf43cd254131ad4e6634fc855`，由 `./dev.sh build` 构建，实际使用 Release O2、JIT ON、IPO OFF。运行前冻结 rut 与 converter 的副本；SHA256 见 [provenance.json](provenance.json)。完整构建成功，基准工具 33 项自测通过。
- nginx 1.29.7，沿用仓库固定镜像 `nginx@sha256:1854da86e82d5dfb49a8f3d78b099adcc7e36608b207146ed95cd47937938a40`。沿用上次的 BoringSSL wrk 二进制，SHA256 为 `d7866c40dcb47f67138cdc420c346272d06b7b5dfc2705161178c996b6e7cf30`。没有新增工具或依赖。
- 同一台 i7-10700 Linux 主机，本机回环网络。单 worker 前端 CPU 2，上游 nginx CPU 3，客户端 CPU 4、5，均为不同物理核。双 worker 前端使用 CPU 2、6。没有锁定频率或独占整机。
- 主矩阵为 HTTP/HTTPS × 四种正文大小 × 静态/代理 × 短/长连接 × 并发 1/32/128。每个引擎每坐标三次，1 秒预热，至少 5 秒正式测量；首轮 nginx 先测，随后交替顺序。所有 Rut 前端实际使用 io_uring，默认连接容量未降低。
- 静态使用 `native-body`，代理使用 `converter-strict`，长连接使用隐式 HTTP/1.1 persistence。该代理模式完整缓冲 Content-Length 响应并执行 deadline/policy 校验，上游连接复用禁用；nginx 使用基准脚本的既有代理缓冲设置。原生流式代理另测，不能把两个模式的结果合并。
- HTTPS 固定 TLS 1.3、TLS_AES_256_GCM_SHA384、X25519，短连接禁用会话恢复并进行完整握手。wrk 的请求延迟从发送 HTTP 请求起计，不含建连和 TLS 握手；RPS 包含这些阶段的成本。p99 是每轮 p99 的中位数，非合并直方图。
- RSS 为前端父进程及直接子进程的总和，nginx 共享页可能重复计数，Rut 包含编译器/JIT。内存映射诊断每个 Rut PID 约每 10 秒只读采样一次；热点采样在正式性能测量结束后单独运行。

## 主要不足和复测

复测首轮改为 Rut 先测。64 KiB 代理单连接使用五轮、每轮 8 秒、1 秒预热；其他复测三轮、每轮 8 秒、2 秒预热。每组均完成预检、预热、测量及清理，全部无错误。

1 MiB HTTP 代理短连接是最大吞吐弱项：主矩阵慢 31%–35%，反转顺序后仍慢约 31%–32%；其 p99 也明显更高。64 KiB HTTP 代理单连接慢约 10%–11%，HTTP 1 MiB 静态长连接在并发 32/128 下慢约 10%–11%。小响应 HTTP 代理单连接及部分静态短连接的差距较小，接近平局的坐标不据此宣称稳定退化。

HTTPS 1 MiB 代理并发 128 的吞吐约慢 11%–13%。反转顺序复测时短连接的请求阶段 p99 为 Rut 240.459 ms、nginx 13.727 ms。这个请求阶段排队现象可复现，但不等于包含 TLS 握手的端到端 p99 放大同样倍数；本次没有测完整连接生命周期的延迟直方图。

## 原生流式代理与双 worker

原生流式比较为 256 KiB 确定性正文、并发 1/32、上游复用开启、nginx proxy_buffering off，每次 1 秒预热、至少 5 秒正式采样、三轮。慢读者和后继请求的完整正文校验、100 次下游复用，以及上游连接计数连续性校验均通过。双 worker 比较为 64 KiB converter-strict 代理长连接、并发 32/128，CPU 分配与旧报告相同。

这些补充场景都领先 nginx。双 worker 的单核上游在 Rut 负载下约占用 57%–78% CPU；原生 HTTP 并发 32 的上游约占用 80% CPU，后续扩容应继续检查上游和客户端容量。

显式 `Connection: keep-alive` 的 HTTP/HTTPS 64 KiB converter-strict 代理长连接并发 32 冒烟测试均通过。该两组只有一轮、2 秒采样，只确认这组请求可预检并无压测错误，不计入性能目标。

## 内存和热点证据

连接槽按需触页合并后，当前双 worker RSS 为 126–146 MiB。旧研究版相同四个坐标为约 239–254 MiB；当前约降低 43%–48%，nginx 当前为 23–38 MiB。两个构建包含其他代码差异，这个跨版本对比不能把全部下降独立归因于一个 commit。当前 `init_lazy` 和 `slots_initialized` 的实现确实避免了启动时触及未使用连接槽。

单 worker 小响应的 Rut RSS 约 76–85 MiB。208 次 /proc 内存诊断覆盖 93 个前端进程，LLVM 驻留页约 48–51 MiB；这是当前固定工作集的重要来源。该映射采样没有与每条吞吐样本同步，也不等于精确峰值或 nginx PSS 对比。详见 [memory-analysis.json](memory-analysis.json)。

三个独立 `cycles:u` 平面采样及两个 DWARF 调用栈采样均成功，无 lost samples。诊断吞吐不进入正式结果。详见 [profiles.json](profiles.json) 和对应文本报告。

- **1 MiB 严格缓冲代理**：平面采样中 memmove 48.80%、memset 14.53%；调用栈把搬运定位到 `ResponseBodyChain::append`，清零定位到 `SlicePool::free_bulk`。这是已验证的用户态热点。进程 CPU 时间中用户态约占 22.6%、内核态约占 77.4%；这些样本比例不能直接当作全部 CPU 时间或可回收的吞吐收益。
- **64 KiB 代理单连接**：响应头解析及扫描、deadline owner/post-commit、policy bundle 校验等占据明显用户态份额，memmove 10.82%。源码仍会重新解析 pinned header；带字节验证的缓存是值得重新评估的候选。此场景用户态时间约占总 CPU 时间 20.8%。
- **1 MiB 静态长连接**：memmove 约 28%，调用栈主要来自 `handle_jit_outcome` 中复制首段到普通发送切片；随后发送余下正文才使用 sendfile。此场景用户态时间仅约占总 CPU 的 5%，正式测量前端 CPU 也未饱和。减少首段复制或校验是候选，尚不能解释全部吞吐差距，需要继续分析发送批次、唤醒与内核成本。

## 建议的下一步

1. 优先处理 1 MiB 完整响应缓冲路径：评估复用已有 `reserve_tail/write_ptr/commit` 让接收直接落到响应链，减少 append 搬运；检查 bulk 缓冲回收的清零范围和时机。现有回收保证旧请求字节不可见，任何变更需要验证长度、所有权及两个后端的失败、取消、关闭和回收路径。
2. 对 64 KiB 单连接代理去除重复解析和可重复计算的校验。先评估带字节验证的 pinned-header parse cache，保持 owner/deadline 语义；通过候选/基线交替控制实验证明收益后再落地。
3. 分别研究 HTTP 静态长连接的发送调度和 HTTPS 大响应短连接的握手/请求调度。当前只定位了部分用户态热点，内核路径和完整握手延迟仍未采样。
4. 中期评估编译器与服务进程的工作集隔离或 JIT 完成后的驻留回收，同时复核热更新与 JIT 生命周期。保留当前连接容量、分片归属和分配器契约。

## 与旧报告的关系和验证边界

[2026 年 9 月 29 日报告](../proxy-performance-2026-09-29/README.md)使用冻结的研究版，包含 `96ebc026` 的响应头解析缓存。该 commit 不是本次源码的祖先，当前 pinned-header 校验实现也没有该缓存。旧报告的 94/96 吞吐领先不能当作当前干净 main 已达到的结果，也不能把本次与它的差异直接称为最近修正引入的回归。

本次验证的是 Linux、本机回环、HTTP/1.1、确定性正文和上述 worker 数。没有覆盖 HTTP/2、上传、实际网络 RTT、会话恢复、长期稳定性、复杂路由和 epoll 性能。吞吐阶段无逐响应正文 Lua 回调；完整正文比较在预检进行。生产源码未修改，因此没有另跑全套运行时单测；完整构建和基准工具自测已通过。

第一次尝试被 SELinux 阻止 nginx 读取新目录，32 个子运行均在就绪前退出，未产生测量样本。失败记录保留在证据归档的 `single/`；仅给本次专用输出目录设为 container_file_t 后，重新运行的 `single-r2/` 才进入正式结果。Docker 通过现有 docker 组权限访问；未提升权限、禁用 SELinux 或拉取新镜像。
