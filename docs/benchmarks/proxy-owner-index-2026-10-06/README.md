# 响应 I/O 批次的 owner 查找优化

2026-10-06。运行时代码提交 `82105e46`，基于已实现 origin 复用的 `576ae9ff`。尚未推送或创建 PR。此次是候选优化，尚未证明 1 MiB 代理吞吐、p99 提升或长连接无退化。

## 改动

原先每批 I/O 事件发现响应 owner、处理精确计时器和终态取消、关联事件时反复扫描最多 256 个 owner。现在增加 shard 内固定 512 槽索引；批次开始清空，批次结束停用，不保留 Connection 指针或跨批次 generation 状态。generation、episode、timer、取消、回收判定保持原样。索引采用线性探测，通常减少全表扫描，但全部碰撞时最坏情况仍为线性查找。只增加约 1 KiB 的 shard 内 scratch 空间，无动态分配或新依赖。

此前识别出的批次结束连接槽扫描没有在本次改动中删除，避免缺少完整验证时改变唤醒/取消路径。此次也未改变接收/发送批次、4 KiB 发布语义或连接复用准入。

## 查找微基准

同一可执行文件交替调用真实运行时的线性查找回退和新索引，各组四次、每次一百万次查找，绑 CPU 6。使用连续连接 ID，包含查找缺失项；各模式校验和一致。只测 owner 查找，不含索引构建/清空、CQE 校验、系统调用或网络传输，不能将下面倍数视为代理提速。

| owner 数 | 线性查找 ns/次 | 索引查找 ns/次 | 查找速度比 |
| ---: | ---: | ---: | ---: |
| 1 | 7.290 | 2.444 | 3.0× |
| 32 | 9.466 | 2.574 | 3.7× |
| 128 | 28.749 | 2.789 | 10.3× |
| 256 | 46.124 | 2.607 | 17.7× |
