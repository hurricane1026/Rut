# Rut / nginx 弱项优化对照 · 2026-10-03

本轮复测响应头解析缓存，**未保留运行时改动**。64 KiB 单连接改善很小，1 MiB 短连接有所改善，但反向顺序的 1 MiB 长连接下降约 5.3%；不足以证明该候选适合当前 main。下一轮仍优先处理大响应完整缓冲路径，而不是根据旧研究版矩阵直接恢复缓存。

## 条件与候选

基线源码为 `1e460cf7a9b0a5d69640de50b7ee5f8e7eddf730`，与 [10 月 2 日主矩阵](../nginx-main-2026-10-02/README.md)相比已包含编译器子进程拆分。基线与候选分别冻结 `rut`、`rut-compile` 和 converter，哈希和完整改动见 [provenance.json](provenance.json)。候选沿用研究 commit `96ebc026` 的实现，只复用固定响应头的语法解析：地址、长度及所有字节相同才能命中，仍逐次校验状态码、正文长度和当前响应策略。缓存为每线程单项，超过 256 字节的头仍重新解析。候选及新增测试保存为 [rejected-cache.patch](rejected-cache.patch)。

使用仓库固定 nginx 1.29.7 镜像和既有 BoringSSL wrk，没有新增依赖。Linux 本机回环、HTTP/1.1、单 worker/shard、隐式 keepalive、converter-strict 完整响应缓冲代理。前端 CPU 2、上游 CPU 3、客户端 CPU 4/5；没有独占主机或锁定频率。每个正文大小均按 **基线→候选→候选→基线** 运行；每组两种连接模式、每引擎三轮、1 秒预热与 5 秒正式测量，组内 Rut/nginx 顺序交替，首引擎随组号反转。准确命令见 [plan.json](plan.json)。

全部 8 组正常完成，共 96 个正式样本；全部响应预检通过，正式及预热无网络、超时或状态错误。逐组、逐轮数据见 [results.json](results.json)、[summary.json](summary.json) 和 [status.json](status.json)。

## 吞吐结果

每个方向的变化均由三轮 Rut RPS 中位数计算；左列为先基线后候选，右列为先候选后基线。Nginx 归一化变化使用各组 Rut/nginx 中位数比值再比较，并非逐请求配对统计。

| 场景 | 并发 | Rut RPS 变化：正向 / 反向 | Nginx 归一化变化：正向 / 反向 |
|---|---:|---:|---:|
| HTTP 64 KiB 代理短连接 | 1 | +0.58% / +0.91% | -0.17% / +0.60% |
| HTTP 64 KiB 代理长连接 | 1 | +0.98% / +0.82% | +0.81% / +1.49% |
| HTTP 1 MiB 代理短连接 | 32 | +1.72% / +3.57% | +1.65% / +3.94% |
| HTTP 1 MiB 代理长连接 | 32 | +0.38% / -5.30% | +0.41% / -5.64% |

1 MiB 长连接最后的基线组中位数从第一组的 1,485 req/s 变为 1,567 req/s；候选两组为 1,490 / 1,484 req/s。该结果不能确定缓存必然引入 5.3% 回归，但足以否定“本次实验已证明它稳定提高吞吐”。没有测统计显著性，也没有重跑全部矩阵。候选所有坐标仍落后 Nginx；四个坐标的 Rut/nginx 比值分别约 0.90、0.90、0.67–0.68、0.73。

## 后续优先级

1. **1 MiB 完整缓冲代理**：主矩阵最大的吞吐缺口。已有采样定位到 `ResponseBodyChain::append` 搬运和 `SlicePool::free_bulk` 清零。本轮解析缓存没有解决它。下一候选应针对接收/搬运本身，使用已有 `reserve_tail/write_ptr/commit`，先证明直接接收目标的所有权、长度上限和异步生命周期，再做性能对照。
2. **64 KiB 单连接代理**：缓存候选不足以证明稳定收益，应继续定位 deadline/policy 校验与接收完成数量；保留现有校验契约。两个顺序和短/长连接都必须测，不能只选择有利组。
3. **HTTP 1 MiB 静态长连接**：研究首段复制、发送批次、sendfile 和唤醒成本。原采样用户态占比低，只减少 memcpy 不足以解释全部差距。
4. **HTTPS 1 MiB 高并发代理**：单独研究握手与请求阶段排队，补完整连接生命周期延迟；不把请求阶段 p99 当成含 TLS 握手的端到端 p99。

直接接收目前只有接口，严格缓冲仍走 separate multishot ring。切换时不得在旧 recv 仍拥有目标时释放或重绑定缓冲；还要检查同批正数/EOF、超时、取消、关闭、正文结束后的额外字节、分配失败及 epoll 路径。现有清零保证保持不变，不通过缩小连接容量或删掉策略校验制造性能收益。

## 验证与边界

候选 `rut`、`rut-compile` 与网络测试构建成功。新增测试检查同地址无效/有效字节改写及恢复、状态码/连接策略/Server 策略变化、另一地址和超过缓存上限的响应头。网络测试 **1,525 项通过、343,931 次检查无失败、1 项跳过**（`current_partial_send_resubmits_with_current_episode` 报 io_uring unavailable）。[网络日志](network-tests.log)、[新增测试日志](cache-tests.log)和 [33 项基准工具自测](harness-tests.log)均保留。改动文件 clang-format 与 `git diff --check` 通过。

性能对照完成后撤回生产代码和测试改动，恢复原实现并重建服务端。此记录只说明候选实验结果；没有验证 HTTPS、其他并发、epoll 性能、HTTP/2、真实网络 RTT 或长期稳定性，未运行 clang-tidy 和完整 CTest。原始环境、生成配置、正文预检、wrk/CPU/服务端日志见 [evidence.tar.gz](evidence.tar.gz)，不包含可执行文件或私钥。首轮构建期间 `/tmp` 用户配额耗尽，正式采样改用工作区同级专用目录，未清理其他任务的文件；全部正式测量在编译及测试结束后串行运行。
